# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Pentaract is a self-hosted file storage service that uses Telegram channels as distributed chunk storage. Go backend (Chi router, PostgreSQL via pgx), React frontend (Vite, MUI 7). Files are split into ~19.9 MB chunks, encrypted with AES-256-GCM, and stored as Telegram messages.

## Commands

```bash
# Development (live reload: Go + Vite)
make dev-up              # API on :8000, UI on :3000

# Production
make up                  # Docker Compose full stack
make down

# Tests
make test                # Go + UI tests in container
go test ./...            # Go tests locally
cd ui && pnpm test       # UI tests locally (node:test, not vitest)
cd ui && pnpm lint       # ESLint (rules-of-hooks + exhaustive-deps); CI runs it

# Single Go test
go test -run TestName ./internal/service/

# Build
make build               # Go binary in container
cd ui && pnpm run build  # Frontend build

# Backup
make backup-now          # Run a one-off DB backup immediately
make backup-list         # List available backups
make backup-restore BACKUP=<file>  # Restore from a backup

# Other
make check               # go vet
make dev-shell           # Shell in dev container
make ui-install          # pnpm install in container
```

## Architecture

### Wire-up: `internal/server/server.go`

All dependency injection happens in `New()`:
Repositories → Telegram Client → WorkerScheduler → StorageManager → Services → Handlers → Chi Router

### Key data flow

**Upload**: Handler reads multipart stream → `io.Pipe` → `StorageManager.Upload` reads chunks from pipe → encrypts each chunk (AES-256-GCM) → uploads 10 chunks in parallel to Telegram → verifies each chunk by re-downloading and SHA-256 hashing → saves to DB.

**Download**: Handler → `StorageManager.DownloadToWriter` → lists chunks from DB → downloads in parallel (1 goroutine per worker) → decrypts → writes to `http.ResponseWriter` in order via `runOrderedJobs`.

**Progress tracking**: All long operations (upload/download/delete) support real-time SSE via `pollSSE()` helper in `progress_tracker.go`. Frontend subscribes before starting the operation.

### Packages

- `internal/telegram/` — Telegram Bot API client with rate-limit retry (`doWithRateLimitRetry`), transient error backoff
- `internal/service/` — Business logic. `StorageManager` is a facade over `ChunkUploader` (`chunk_uploader.go`), `ChunkDownloader` (`chunk_downloader.go`) and `ChunkDeleter` (`chunk_deleter.go`), which share a `chunkTransport` (scheduler, Telegram client, `ChunkCipher`). Build it with `NewStorageManager` (or `newStorageManager(storageDeps{...})` in tests)
- `internal/handler/` — HTTP handlers. `FilesHandler` embeds `UploadHandler` (`upload_handler.go`, `local_fs.go`) and `DownloadHandler` (`download_handler.go`) and adds tree/search/move/delete. SSE polling unified in `progress_tracker.go`. `DeleteTrackers` (delete progress registry) is injected into both the files and storages handlers. Inline previews (`?inline=1`) of any type are served through the chunk range path and never tracked. `MediaHandler` (`media_handler.go`) describes Matroska files (`/files/media_info/*`) and serves them as HLS (`/files/hls/*`, `/files/hls_stop/*`); `/api/internal/hls_source/{token}` is the loopback-only ranged stream ffmpeg reads from (no JWT, token minted per session)
- `internal/media/` — Minimal Matroska/EBML header parser (`ParseMatroska`: duration, tracks, codec IDs) and the HLS `Plan` (copy H.264/HEVC and AAC, transcode the rest). No ffprobe involved
- `internal/service/hls.go` — `HLSService`: one ffmpeg process per (user, file, audio track) writing fMP4 segments into `HLS_CACHE_DIR/session-*`. A segment request is served from disk, waited for (≤ `hlsMaxWaitAhead` segments ahead) or triggers a restart at that segment (`-ss` input seek + `-copyts` keeps original timestamps, `-start_number` keeps numbering). The playlist is generated by Go (uniform segments from the header duration); real segments cut at keyframes and run a little long, which hls.js realigns from the fragment timestamps. Idle sessions are reaped; `media_info` is cached per file ID. Only the web UI uses this: Kodi and other players keep the native `?inline=1` stream
- `internal/service/watch_progress.go` — `WatchProgressService`: where each user is in each video, shared by the web UI and Kodi. One `watch_progress` row per (file, user), upserted in place (never appended) and removed with the file or user by `ON DELETE CASCADE`. Players report raw positions to `PUT /files/watch_progress/*`; the server applies the rules (`WatchResumeMinSeconds`, `WatchedFraction`; a report never clears `watched`). Hand marks (web menu "Mark as watched/unwatched", Kodi context menu) go to `PUT /files/watched/*` with `{"watched": bool}`, which sets `watched` outright and drops the resume point. `Tree` and `Search` add a `watch` object to the files the user has played. Clearing deletes the user's rows: all of them with `DELETE /watch_progress` (header play icon menu), or those under a folder, recursively, with `POST /files/clear_watch_progress/*` (folder menu; POST because `DELETE /files/*` would take it for a folder path)
- `internal/repository/` — PostgreSQL queries. `files.go` has the complex path-based queries (ListDir, Search, CreateFileAnyway with dedup)

### Frontend

- `ui/src/api/` — API client with shared SSE subscription (`subscribeAuthSSE`)
- `ui/src/pages/Files/` — Main file browser, split into hooks: `useUploads`, `useDownloads`, `useDeleteOperation`, `useBulkOperations`, `useFileNavigation`, `useFileSelection`. `useUploadConflicts` (conflict dialog + directory cache) is shared with `pages/LocalUpload`; `common/use_delete_progress.js` is shared with `pages/Storages`
- `common/use_api_action.js` — `run(action, { success, onSuccess, onError })` replaces the try/await/addAlert boilerplate in pages. API failures are `ApiError` with a `status` (`api/request.js`)
- `common/completion_registry.js` — awaitable terminal status per transfer; bulk uploads and bulk downloads use it to run one file at a time
- Dialogs that edit an entity (`EditWorkerDialog`, `GrantAccess`, `RenameFolderDialog`) initialise state from props and are reset by the parent through `key`, not by effects
- Shared components: `Panel` (bordered surface), `PathBreadcrumbs` (Root > a > b), `ProgressCard`, `AuthForm` (login/register form; the page only supplies the submit call). Progress components take the hook state objects spread as props (`<UploadProgress {...uploadState} />`), so state keys and prop names must stay aligned
- `common/use_async_value.js` — `useAsyncValue(API.x.y, fallback)` loads a value once on mount (storages lists, admin status); pass a stable loader and a module-level fallback
- Pure, node-tested modules hold the logic hooks and components lean on: `common/progress.js`, `common/api_action.js`, `pages/Files/operations.js`, `pages/Files/upload_conflicts.js`, `pages/LocalUpload/local_upload_paths.js`
- Storage paths inside URLs go through `encodePath` in `ui/src/api/index.js` (per-segment `encodeURIComponent`); the server decodes with `url.PathUnescape`
- `ui/src/components/ProgressCard.jsx` — Shared progress UI used by all 4 progress components
- Watch progress: `common/watch_progress.js` (pure: when to report, what to ignore) and `common/use_watch_progress.js` (hooks it to a `<video>`). Both players (`NativeVideoPlayer`, `HlsPlayer`) resume at `file.watch.position_seconds`, show `ResumeNotice`, and also save on `pagehide` (closing the tab unmounts nothing). In the file list a playable video shows its `watchState` instead of the file icon: stop (unplayed), play (started), check (watched; under 10% left counts as finished, decided server-side). Positions read while the video is seeking or has no frame are ignored, because a fresh or reset player sits at 0 and would wipe the resume point
- Both video players render their `<video slot="media">` inside `PlayerFrame` (Media Chrome controls, lazy-loaded with the players) instead of the browser's native controls, because Chrome's seek bar shows no time on hover. The video stays a React-rendered element, so hls.js and `useWatchProgress` attach to it as before
- Play queue: `common/play_queue.js` (pure) picks the next playable video after the open one in the listing as shown (folder or search results). When a video ends and autoplay is on, `MediaPreviewDialog` calls `onPlayNext` and the next player mounts with `autoPlay` (players are keyed by path, so each file gets a fresh `<video>` and HLS session). The Autoplay on/off toggle is remembered per browser in `localStorage` (`autoplay_next`, default on)
- `getMediaType` returns `'hls'` for `.mkv`; `MediaPreviewDialog` then lazy-loads `HlsPlayer.jsx` (hls.js with `Authorization` header via `xhrSetup`, native HLS with `?access_token=` only where MSE is missing). Pure helpers and the hls.js config (long first-byte timeouts for Telegram latency) live in `common/hls_playback.js`

## Configuration

All via environment variables (see `.env.example`). Key ones:

- `SECRET_KEY` — JWT signing secret. Also derives the chunk encryption key (PBKDF2, 600k iterations) unless `ENCRYPTION_KEY` is set. Changing it breaks files encrypted with it.
- `ENCRYPTION_KEY` — Optional dedicated chunk encryption secret. `ChunkCipher` keeps `SECRET_KEY` as a decrypt-only fallback so files uploaded before the switch stay readable (`NewChunkCipherWithFallback`).
- `TELEGRAM_RATE_LIMIT` — Requests per minute per worker (default 18)
- `FFMPEG_PATH`, `HLS_CACHE_DIR`, `HLS_SEGMENT_SECONDS`, `HLS_IDLE_TIMEOUT_SECS` — MKV playback pipeline. ffmpeg is in the Docker images; without it the UI reports MKV playback unavailable instead of failing
- `ALLOW_REGISTRATION` — `true` opens self sign-up (`/register`, `POST /api/users`). Off by default: the superuser (`SUPERUSER_EMAIL`, created on startup) adds accounts from User Management (`POST /api/users/manage`). `GET /api/users/registration` (no auth) tells the login page whether to show the sign-up link
- `DB_MAX_CONNS` — Postgres pool size (default 32). The legacy `WORKERS` variable is still read as `WORKERS * 8`.

## Testing patterns

**All new features and bug fixes must include tests.** Backend changes need Go tests; frontend changes need JS tests. Do not submit code without corresponding test coverage.

**Go handlers**: Mock service interfaces with function fields (`mockFilesService`), use `httptest`. See `internal/handler/files_handler_test.go`.

**Go services**: Fake repository interfaces. See `internal/service/files_test.go`; `StorageManager` takes `chunksRepository`/`storageGetter` interfaces so upload tests use in-memory fakes (`chunk_uploader_flow_test.go`).

**Frontend**: Node.js built-in `test` module (NOT vitest). Run with `pnpm test` which calls `node --test`.

## Gotchas

- `crypto.randomUUID()` not available in insecure HTTP contexts — `ui/src/common/operation_id.js` has a fallback using `crypto.getRandomValues()`
- No HTTP read/write timeouts on the server (large transfers can take hours) — per-request context cancellation instead
- Download auth via `?access_token=` query param (for iframe-based downloads) — only allowed on `/files/download/`, `/files/download_dir/` and `/files/hls/` paths; the access log redacts it
- HLS segment requests may legitimately take minutes (a seek means downloading and decrypting a ~20 MB chunk from Telegram before ffmpeg emits anything); hls.js defaults would time out at 10 s, so `buildHlsConfig` raises them. Never add an HTTP timeout to those routes
- Chrome's macOS hardware decoder (VideoToolbox) rejects some Blu-ray H.264 that copies cleanly into HLS and that Kodi and ffmpeg decode fine: the media panel shows `VTDecompressionOutputCallback -12909` / `video decode error!` after a few seconds. The segments themselves are valid (each decodes standalone). `HlsPlayer` answers a `MEDIA_ERR_DECODE` on copied video by reloading with `?transcode=1` (`HLSVariant.TranscodeVideo`, its own ffmpeg session, libx264 capped at 1920 px wide) from the same position, once
- HLS fMP4 segments are written with `-hls_segment_options use_editlist=0`. By default the MP4 muxer moves a track's start offset (MKV audio starting ~1 s after the video, or the keyframe before a `-ss` seek) into an edit list and rebases the track to zero; MSE ignores edit lists in fragmented MP4, so audio played up to ~2 s early in the browser while ffprobe and desktop players looked fine. That alone was not enough: Chrome also plays MSE audio frames back to back, ignoring timestamp gaps (media panel: "Failed to reconcile encoded audio times with decoded output"), and without edit lists the muxer still starts each track at zero by stretching the first frame of the later one. So transcoded audio goes through `hlsAudioFilter` (`aresample` fills gaps with silence; `first_pts` makes audio start 0.5 s before the video so the stretched frame is a video frame) and copied video after a seek uses `-noaccurate_seek`. `hls_sync_test.go` measures this end to end with real ffmpeg (flash/beep markers, audio played back to back); judge A/V changes by it, not by `tfdt` or `ffprobe start_time`. Copied AAC audio cannot be filtered and keeps any start gap
- The `*.test.go` for the HLS pipeline use a shell-script fake ffmpeg (`hls_test.go`); `hls_ffmpeg_test.go` runs the real binary when it is on PATH and skips otherwise
- MKV subtitles are dropped on purpose (`-sn`). The plan to add them, with the constraint that they must come out of the same ffmpeg session as the video (extracting a track up front re-downloads the whole file from Telegram), is in `docs/plans/mkv-subtitles.md`
- Progress SSE subscriptions stop on 401/403/404 (`SSE_FATAL_STATUSES` in `ui/src/api/index.js`) and keep reconnecting on other failures
- Over plain HTTP, Chrome blocks downloads of file types outside its safe list (e.g. `.7zip`, `.zip`, `.pdf`) as "insecure" and closes the connection; it re-requests the same URL when the user allows the file. `failTracker` in `download_handler.go` keeps such downloads in an `interrupted` state (SSE status `interrupted`) instead of failing them, so the resumed request continues the same progress card
- The upload handler answers only after the multipart body has been consumed. If a handler starts writing while the request body is unread, `net/http` discards the rest of a body under 256 KB (`maxPostHandlerReadBytes`), which silently truncated every small browser upload to the ~3 KB the multipart parser had buffered. `runTrackedUpload` wraps source read failures in `domain.ErrUploadInterrupted` and `uploadChunks` aborts on any read error other than `io.EOF`/`io.ErrUnexpectedEOF`, so a cut-short source fails the upload instead of persisting a truncated file
- The web UI is meant to be used through the nginx front (`nginx/pentaract.conf`, `https://host:8443`). Over plain HTTP/1.1 the browser's 6-connections-per-host limit, shared by all tabs, is used up by uploads (POST + one progress SSE per file) and other tabs stall. The nginx config must keep `proxy_buffering`/`proxy_request_buffering` off and the 24 h timeouts (same reason as the no-timeouts rule above), log `$uri` without query args (`?access_token=`), and keep `/api/internal/` blocked. `make up` runs `make certs` (self-signed, kept if present). `scripts/test-nginx-config.sh` checks the cert script and runs `nginx -t`
- DB migrations run automatically on startup (`internal/startup/startup.go`)
- `ui/dist/` is gitignored — Docker builds it fresh; local dev uses Vite dev server
